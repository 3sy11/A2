# A0 — 场景故事

> 步骤 1：用一句话描述核心使用场景，不涉及类名。每个故事明确**谁触发、做了什么、返回了什么**。

---

## 一、基础对话

### S01. 直答（无工具）

**触发**：用户在 CLI 输入"什么是依赖注入？"
**过程**：Agent 将问题连同角色提示词发给 LLM，LLM 直接生成文字回答。
**返回**：用户收到文字回答，无工具调用，无文件读写。

### S02. 单工具调用

**触发**：用户输入"读一下 auth.py"
**过程**：Agent 将问题发给 LLM → LLM 返回工具调用指令（读文件）→ Agent 在本地终端读取 auth.py → 文件内容作为观察结果回传 LLM → LLM 输出文件内容摘要。
**返回**：用户收到 auth.py 的内容展示。

### S03. 多轮工具 + 分析

**触发**：用户输入"审查 auth.py 的安全问题"
**过程**：Agent 将问题发给 LLM → LLM 要求读文件 → Agent 读取 auth.py → 观察结果回传 LLM → LLM 分析代码，发现 SQL 注入和明文密码问题，生成审查报告。
**返回**：用户收到结构化的安全审查报告（漏洞列表 + 修复建议）。

---

## 二、规划与编排

### S04. 任务规划 + 逐步执行

**触发**：用户输入"重构整个认证模块"
**过程**：Agent 先调用 LLM 将目标分解为子任务列表（如：分析现有代码 → 设计新接口 → 逐文件重写 → 跑测试）→ 子任务列表写入磁盘 → Agent 按顺序逐个执行每个子任务（每个子任务走 S03 的工具循环）→ 每完成一个子任务向用户报告进度。
**返回**：用户收到逐步进度反馈 + 最终汇总报告。

### S05. 多角色并行

**触发**：用户输入"对比 staging 和 production 的配置差异，生成迁移方案"
**过程**：Orchestrator 角色调用 LLM 规划 → LLM 决定并行派出两个子角色 → Orchestrator 同时启动 staging_reader 和 prod_reader → 两个子角色各自独立读取对应环境的配置文件 → 两份结果返回给 Orchestrator → Orchestrator 调用 LLM 对比差异，生成迁移方案。
**返回**：用户收到配置差异对比 + 迁移方案文档。

### S06. 子角色失败回退

**触发**：S05 执行中，prod_reader 因权限不足无法读取 production 配置
**过程**：prod_reader 工具调用返回权限错误 → prod_reader 的 LLM 判断无法完成 → 返回失败结果给 Orchestrator → Orchestrator 的 LLM 看到失败信息，决定改用 ask_user 工具向用户请求 production 配置 → 用户手动粘贴 → Orchestrator 继续对比。
**返回**：用户被询问后提供了配置，最终仍收到迁移方案。

## 三、工具与权限

### S07. 危险操作审批

**触发**：用户输入"执行部署脚本 ./deploy.sh"
**过程**：Agent 调用 LLM → LLM 返回 bash 工具调用 → Agent 检查权限规则，bash 命中 approve 规则 → Agent 中断执行，向用户展示"即将执行 bash(./deploy.sh)，是否允许？" → 用户确认"y" → Agent 执行脚本 → 脚本输出回传 LLM → LLM 生成执行结果摘要。
**返回**：用户确认后收到脚本执行结果。

### S08. 外部工具（MCP）

**触发**：用户输入"查一下 PR #42 的构建状态"
**过程**：Agent 调用 LLM（工具列表包含 MCP 注册的 GitHub 工具）→ LLM 返回 MCP GitHub 工具调用 → Agent 通过 MCP 协议将请求转发给 GitHub MCP Server → GitHub Server 调用 GitHub API → PR 详情返回 → Agent 将结果回传 LLM → LLM 生成可读摘要。
**返回**：用户收到 PR #42 的状态、失败原因、相关 commit 信息。

### S09. 权限拒绝

**触发**：用户输入"删除 /etc/passwd"
**过程**：Agent 调用 LLM → LLM 返回 bash 或 write_file 工具调用 → Agent 检查权限规则，命中 block 规则 → Agent 不执行工具，直接将"权限拒绝"作为观察结果回传 LLM → LLM 向用户解释无法执行。
**返回**：用户收到拒绝说明，工具未执行。

## 四、记忆与上下文

### S10. 长对话自动压缩

**触发**：用户与 Agent 已对话 20 轮，下一轮 build_messages 时 token 总量超过阈值
**过程**：Agent 检测到 token 超限 → 第一层：规则截断远距离的工具输出 → 仍超限 → 第二层：查找已有会话摘要替换旧消息 → 仍超限 → 保护动作：调用便宜 LLM 从即将丢弃的对话中提取洞察写入记忆库、提取事实写入事实库 → 第三层：调用 LLM 生成结构化摘要替换旧消息 → 压缩后 token 回到预算内。
**返回**：用户无感知，对话正常继续，之前的关键信息已持久化到记忆中。

### S11. 跨会话回忆

**触发**：用户输入"上次你帮我改的那个 CI 配置在哪"
**过程**：Agent 在 build_messages 时从事实库中用关键词检索 → 命中之前 Memory Flush 写入的事实"CI 配置路径: .github/workflows/ci.yml" → 该事实注入到 LLM 的 system prompt 中 → LLM 据此回答。
**返回**：用户收到准确的文件路径和上次修改的摘要。

### S12. 技能自动匹配

**触发**：用户输入"帮我做代码审查"
**过程**：Agent 在 build_messages 时用"代码审查"匹配技能库 → 命中 code-review 技能（关键词: review, security, 审查）→ 从文件系统读取技能正文（一份完整的审查工作流指南）→ 作为 system reminder 注入 LLM prompt → LLM 按照工作流指南执行（先读文件、再逐项检查、最后输出报告）。
**返回**：用户收到按标准工作流执行的审查报告，而非 LLM 随意发挥的回答。

## 五、技能结晶

### S13. 手动触发结晶

**触发**：管理员通过 HTTP 接口调用结晶命令，指定某个历史会话 ID
**过程**：系统从会话归档中读取该会话的完整对话记录 → 调用 LLM 提取可复用的执行模式（名称、描述、关键词、工作流正文）→ 元数据写入技能数据库 → 工作流正文写入文件系统 → 更新记忆库的技能索引。
**返回**：管理员收到成功响应，新技能立即可被 S12 匹配到。

---

## 六、角色与配置管理

### S14. 角色热更新

**触发**：管理员通过 HTTP 接口修改 devops 角色的 system_prompt
**过程**：系统检查该字段是否支持热更新 → system_prompt 属于热更新字段 → 直接修改运行中的角色定义 → 持久化到角色数据库。
**返回**：管理员收到成功响应，devops 角色的下一轮对话立即使用新提示词，无需重启。

---

## 七、系统生命周期

### S15. 冷启动

**触发**：运维执行 `python -m a2 chat --role code_reviewer`
**过程**：系统收集各模块默认配置 → 读取 agent.toml 覆盖 → 替换环境变量 → 按依赖拓扑排序启动服务（LLM → 环境 → 技能 → 规划 → MCP → Agent）→ 每个服务初始化自己的数据库连接和内存缓存 → 激活命令行指定的角色 → 为该角色创建独立的上下文实例和记忆层 → 等待用户输入。
**返回**：CLI 显示就绪提示，用户可以开始对话。
