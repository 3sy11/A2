# 附件七 — Skill 设计原则与评测体系

> 来源于「慢学AI」多期视频分析（BV1spQSBGErn / BV1HWd6BsEmG / BV1wyosBUEtb / BV1BS6PBMEAr），涵盖 Skill 使用度量、评分器设计、生命周期闭环和成功定义。

---

## 一、先定义什么叫"变好"（Definition of Success）

在优化 Skill 之前，必须先明确评估维度。如果连"什么叫变好"都没写清，后面的评估根本没有靶子。

> OpenAI 在这里已经把评估对象从"最终像不像"推进到了"中间到底发生了什么"。**结果和路径，要一起验。**

### 四个评估维度

| 维度 | 关注点 | 具体问题 |
|------|--------|---------|
| **OUTCOME** | 任务完成了没有 | 应用能不能真的跑起来 |
| **PROCESS** | 路径走对了没有 | 有没有按预期步骤和工具执行 |
| **STYLE** | 输出能不能接手 | 结构、布局、风格是否一致 |
| **EFFICIENCY** | 成本会不会失控 | 有没有 thrashing、乱跑命令、乱烧 token |

## 二、两种评分器组合（Combined）

### 确定性检查

- **目标**：抓底线
- **判断**：基础动作有没有发生
- 例：文件是否创建、命令是否执行、端口是否监听

### 评分细则检查

- **目标**：抓质量
- **判断**：做出来的东西像不像你要的
- 例：代码结构是否符合规范、输出是否包含必要字段

### 锁死输出格式

- **目标**：防漂移
- **判断**：大模型判断每次一致
- 例：JSON Schema 约束评分输出，防止评分器自身漂移

### 接进持续集成流水线

> 一旦进了流水线，这件事就不再依赖某个工程师记得手动去试。它会变成持续运行的回归守门员。

## 三、Skill 成熟后的六类扩展检查（Extending Evals）

Skill 从"能跑"到"生产可靠"，需要逐步增加以下检查：

| # | 检查类型 | 说明 |
|---|---------|------|
| 1 | **命令数检测** | 以前 6 步，现在 18 步？任务完成了，但系统在变差 |
| 2 | **消耗量追踪** | 防止 Skill 越写越胖，每次执行越来越贵 |
| 3 | **构建检查** | 直接跑构建命令，一构建就露馅。成本低，默认开启 |
| 4 | **冒烟检查** | 拉起服务器，发一个请求，看有没有响应。按风险叠加 |
| 5 | **仓库清洁度** | 任务做完了，不代表系统没被弄脏 |
| 6 | **权限回归** | 防止某次改动后悄悄依赖更高权限 |

## 四、Skill 使用度量（Measurement）

### 实现方式

在 settings.json 里挂上 PreToolUse hook，专门记录 Skill 调用：

```
matcher: "Skill"
command: ~/.claude/hooks/log-skill.sh
```

### 会记什么

| 字段 | 说明 |
|------|------|
| 时间 | 调用时间戳 |
| 用户 | 谁触发的 |
| Skill 名称 | 哪个 Skill 被调用 |
| 参数 | 调用时传入的参数 |

### 能回答什么问题

- 哪个 Skill 最常用
- 哪个本来该被调用却很少被调
- 哪个可能该下线

## 五、Skill 的生命周期：从草稿到迭代闭环（Lifecycle）

核心理念：**评测驱动，改完再测，测完再改。**

```
        ① 定义任务
        先说清 skill 要解决什么
              │
              ▼
   ⑧ 继续迭代          ② 写草稿
   带着新证据回到         把流程和约束写进
   任务定义               SKILL.md
        ▲                    │
        │                    ▼
   ⑦ 扩大测试集          ③ 小规模测试
   从少量样本扩到         草稿立刻面对
   稳定验证               测试用例
        ▲                    │
        │                    ▼
   ⑥ 修改 skill          ④ 看结果
   按失败原因改，         看输出哪里对、
   再测一次               哪里偏
        ▲                    │
        │                    ▼
        └──── ⑤ 人工复核 ────┘
              结果和指标展示给人看
```

### 八步闭环详解

| 步骤 | 名称 | 说明 |
|------|------|------|
| 1 | 定义任务 | 先说清 skill 要解决什么 |
| 2 | 写草稿 | 把流程和约束写进 SKILL.md |
| 3 | 小规模测试 | 草稿立刻面对测试用例 |
| 4 | 看结果 | 看输出哪里对、哪里偏 |
| 5 | 人工复核 | 结果和指标展示给人看 |
| 6 | 修改 skill | 按失败原因改，再测一次 |
| 7 | 扩大测试集 | 从少量样本扩到稳定验证 |
| 8 | 继续迭代 | 带着新证据回到任务定义 |

## 六、A2 适配分析

### 当前 A2 Skill 体系映射

| 本文概念 | A2 对应 |
|----------|---------|
| Skill 使用度量 | 当前缺失 — 无 hook 记录 skill 调用 |
| 确定性检查 | 可映射为 Sprint Contract 验收条件 |
| 评分细则检查 | Evaluator 角色（参见 A5） |
| 六类扩展检查 | 当前缺失 |
| 生命周期闭环 | SkillService 有加载机制，缺乏评测迭代流程 |

### 待增强方向

1. **Skill 调用度量**：
   - 在 `SkillService.activate_skill()` 中记录调用事件（时间、用户、skill 名称、触发关键词）
   - 持久化到 session 事件流或独立日志
   - 定期分析：高频 / 低频 / 应调未调

2. **Skill 评测框架**：
   - 每个 Skill 目录增加 `evals/` 子目录，存放测试用例
   - 测试用例定义：输入 prompt + 预期行为（确定性检查）+ 质量评分细则
   - 支持 `a2 skill eval <skill_name>` 命令批量跑测

3. **六类扩展检查集成**：
   - 命令数检测：记录每次执行的 tool call 次数，对比历史均值
   - 消耗量追踪：统计每次 skill 执行的 token 消耗
   - 构建检查：skill 完成后自动跑 `build` 命令
   - 冒烟检查：可选，skill metadata 声明 `smoke_test_command`
   - 仓库清洁度：执行后检查 `git status` 无意外文件
   - 权限回归：对比 skill 声明的 `allowed_tools` 与实际调用

4. **成功定义四维度落地**：
   - Skill metadata 增加 `success_criteria` 字段：
     ```toml
     [success_criteria]
     outcome = "应用能正常启动并响应请求"
     process = "按 read → plan → implement → test 顺序执行"
     style = "代码符合项目 lint 规则，有类型注解"
     efficiency = "总步骤 ≤ 15，token ≤ 50k"
     ```
