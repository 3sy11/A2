# 附件九 — GA 三基础原语与涌现行为

> GA 的架构哲学：用最少的基础原语组合出复杂行为，而非为每种场景设计专用机制。

---

## 一、设计哲学

GA 不追求"功能全面"，而是追求**原语正交**。三个基础原语各自解决一个维度的问题，彼此独立但可自由组合。复杂行为不是预先设计的，而是从简单原语的组合中**涌现**出来的。

这类似 Unix 哲学：`pipe` + `fork` + `file` 三个机制组合出整个操作系统的能力。

---

## 二、三个基础原语

| 原语 | 本质 | 一句话描述 |
|------|------|-----------|
| **自托管 CLI 入口点** | Agent 就是一个命令行程序 | 任何能调用命令行的程序都能调用 GA——包括 GA 自己 |
| **文件协议** | 目录约定的跨进程通信 | `input.txt` 送任务、`output.txt` 流结果、`reply.txt` 续对话、`stop.txt` 终止 |
| **反射模式** | 轮询 + 热重载 | 外部脚本定义触发条件，运行时周期性求值，脚本修改后自动重载无需重启 |

### 原语一：自托管 CLI 入口点

**核心洞察**：Agent 不是库、不是服务、不是 SDK 对象——它就是一个可执行程序。

```
$ ga --task-dir ./my-task
```

**意义**：
- 任何能调用命令行的程序都能调用 GA（CI/CD、cron、其他 agent）
- GA 自己也能调用自己（子 agent = 另一个进程实例）
- 不需要特殊的 SDK 或 RPC 协议
- 进程模型天然提供隔离（独立内存空间、独立上下文）

### 原语二：文件协议

**核心洞察**：进程间通信不需要 RPC/WebSocket/消息队列——文件系统就够了。

```
task-dir/
├── input.txt      ← 送入任务描述
├── output.txt     ← 流式输出结果（追加写入）
├── reply.txt      ← 续对话（追加新轮次）
└── stop.txt       ← 创建此文件 = 终止信号
```

**意义**：
- 跨语言、跨平台、零依赖
- 可用任何文本编辑器观察和调试
- 天然支持持久化（文件就是日志）
- 父子 agent 通信不需要共享内存或网络连接

### 原语三：反射模式

**核心洞察**：不需要事件系统或消息总线——周期性求值 + 热重载就够了。

```
反射循环:
  while running:
      sleep(interval)
      for script in trigger_scripts:
          result = execute(script)
          if result != "":
              dispatch_task(result)
      reload_if_modified(trigger_scripts)
```

**意义**：
- 触发逻辑是普通脚本，任何人都能写、能改、能调试
- 热重载意味着修改触发条件不需要重启 agent
- 轮询间隔可配置，平衡响应速度和资源消耗
- 不需要复杂的事件订阅/发布基础设施

## 三、涌现出的高级行为

三个原语组合，无需额外机制即可实现以下高级行为：

### 1. 子 Agent 并行分发

**组合**：自托管 CLI + 文件协议

**机制**：父 Agent 通过 `code_run` 启动自己的另一个实例，传入不同的 `task-dir`。

```
父 Agent (pid: 1001)
├── code_run: ga --task-dir ./subtask-1/    → 子 Agent (pid: 1002)
├── code_run: ga --task-dir ./subtask-2/    → 子 Agent (pid: 1003)
└── code_run: ga --task-dir ./subtask-3/    → 子 Agent (pid: 1004)
```

**关键特性**：
- 父子是**同构进程**——不存在特权的子 Agent 运行时对象
- 双方遵循**完全相同的文件协议**
- 上下文**天然隔离**（独立进程 = 独立内存空间）
- 不需要复杂的状态管理来区分"哪些历史属于哪个子任务"
- 父 agent 通过读取各 `output.txt` 收集结果

### 2. 看门狗监控

**组合**：反射模式 + 检测环境变化的触发脚本

**机制**：
```bash
# trigger: watch_deployment.sh
if curl -sf https://app.example.com/health > /dev/null; then
    echo ""  # 健康，无事发生
else
    echo "生产环境健康检查失败，请诊断并修复"
fi
```

当脚本返回非空字符串时，该字符串被作为任务分发到标准流水线。不需要专门的监控框架。

### 3. 定时任务调度

**组合**：反射模式 + 检查时间条件的触发脚本

**机制**：
```bash
# trigger: daily_report.sh
if [ "$(date +%H:%M)" = "09:00" ]; then
    echo "生成昨日工作日报并发送到 Slack"
fi
```

跟看门狗共享**完全相同的底层机制**，区别仅在于脚本内容。

### 4. 自主空闲行为

**组合**：反射模式 + "当前无任务"的触发条件

**机制**：
```bash
# trigger: idle_behavior.sh
if [ ! -f ./current-task/input.txt ]; then
    echo "扫描代码库中的 TODO 注释，整理为优先级列表"
fi
```

Agent 在空闲时自动执行预设的探索或维护任务。

## 四、设计优势分析

### 简单性

| 传统方案 | GA 原语方案 |
|----------|------------|
| 子 agent 需要 SubagentRuntime + 状态隔离 + token 归属 | `code_run` 启动新进程 + 文件协议通信 |
| 监控需要事件总线 + 告警规则引擎 | 反射脚本返回非空 = 触发任务 |
| 定时任务需要 cron 集成 + 任务队列 | 反射脚本检查时间条件 |
| 空闲行为需要状态机 + idle 检测 | 反射脚本检查"无任务"条件 |

### 可组合性

原语之间正交，可以自由叠加：
- 看门狗检测到异常 → 启动子 agent 修复 → 子 agent 完成后父 agent 验证
- 定时任务触发 → 多个子 agent 并行执行 → 汇总结果
- 空闲行为中 → 发现问题 → 升级为看门狗持续监控

### 可调试性

- 所有状态都在文件系统中，可直接 `cat`/`tail -f` 观察
- 触发脚本是独立可执行文件，可单独测试
- 进程模型意味着 `ps`/`kill` 就是管理工具

## 五、A2 适配分析

### 当前 A2 对应

| GA 原语 | A2 对应 | 差距 |
|---------|---------|------|
| 自托管 CLI 入口点 | `a2 chat` CLI 命令 | ✅ 已有 CLI 入口 |
| 文件协议 | 无（使用进程内 Command yield） | ❌ 进程间通信依赖内存 |
| 反射模式 | 无 | ❌ 无周期性触发机制 |

### GA 涌现行为在 A2 中的实现路径

| 涌现行为 | A2 当前实现 | 改造方案 |
|----------|------------|----------|
| 子 Agent 并行 | `SpawnAgentCommand` 进程内 | 可选：支持 `a2 run --task-dir` 进程级隔离 |
| 看门狗监控 | 无 | 反射模式 + trigger 脚本目录 |
| 定时任务 | 无 | 同上（脚本内容不同） |
| 自主空闲 | 无 | 同上（检测"无任务"条件） |

### 增强建议

1. **文件协议层（可选）**：
   - 为 `a2` 增加 `--task-dir` 模式，通过文件系统收发任务
   - 好处：支持被外部程序调用、支持进程级子 agent 隔离
   - 不替代现有进程内 Command 机制，作为补充通道

2. **反射模式**：
   - 新增 `a2 watch --triggers ./triggers/` 命令
   - 周期性执行 triggers 目录下的脚本
   - 脚本返回非空时作为 goal 提交给 AgentService
   - 支持热重载（inotify/fswatch 检测脚本变更）

3. **子 Agent 进程隔离（高级）**：
   - 当前 `SpawnAgentCommand` 在同一进程内运行子 agent
   - 可选增加进程级模式：`code_run("a2 run --task-dir ./subtask-1/")`
   - 天然获得内存隔离 + 独立上下文 + 故障隔离
