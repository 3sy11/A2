# 附件八 — 记忆架构：GA 四层记忆模型

> 来源于 GA（Gemini Agent）的记忆管理设计，解决传统方案"不保留历史"或"全量追加"的两难问题。

---

## 一、传统方案的困境

| 方案 | 问题 |
|------|------|
| **不保留历史**（每次从零开始） | 无法利用历史经验，重复犯错，用户需反复教育 |
| **全量追加**（所有历史塞进上下文） | 上下文爆炸，token 成本失控，长对话性能退化 |

两种方案本质上是在"记忆广度"和"上下文成本"之间做粗暴取舍。GA 的四层架构给出了优雅的折中方案。

---

## 二、GA 四层记忆架构

核心隐喻：**图书馆模型** — 你不会把所有书搬到桌上才开始工作，而是先查目录（L1），再去书架取需要的那本（L2/L3）。

| 层级 | 定位 | 是否 always-on | 典型大小 |
|------|------|:--------------:|----------|
| **L1 索引层** | 目录卡片，告诉 Agent "有哪些知识可用" | 是 | ~200 token |
| **L2 事实层** | 环境事实、用户偏好、服务器信息 | 否，按需 `file_read` | 数百~数千 token |
| **L3 SOP 层** | 标准操作流程、技能脚本 | 否，按需 `file_read` | 每个 SOP 数百 token |
| **L4 原始日志** | 完整对话历史，用于追溯和审计 | 否，极少访问 | 无限增长 |

### 核心机制

**L1 始终在上下文中（成本极低），L2-L4 只在需要时才被加载。**

```
┌─────────────────────────────────────────────────────────┐
│                    Context Window                         │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │  L1 索引层 (~200 token) — 永远在场               │   │
│  │  "你有以下知识可用: [用户偏好] [部署SOP] [...]"    │   │
│  └──────────────────────────────────────────────────┘   │
│                                                          │
│  ┌─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┐   │
│  │  L2/L3 按需加载区 — agent 主动 file_read 拉入    │   │
│  └─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┘   │
│                                                          │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  L4 原始日志 — 外部持久化，仅追溯/审计时访问            │
└─────────────────────────────────────────────────────────┘
```

## 三、各层详解

### L1 索引层（~200 token，always-on）

**作用**：告诉 agent 有哪些知识可以使用，但不直接包含知识内容。

**类比**：图书馆的索引目录卡

**示例内容**：
```
你有以下知识源可用（需要时用 file_read 加载）：
- [user_preferences] 用户偏好和工作习惯
- [server_config] 服务器配置和环境信息
- [deploy_sop] 部署标准操作流程
- [debug_playbook] 故障排查手册
- [project_conventions] 项目编码规范
```

**设计要点**：
- token 极小（~200），即使 always-on 也不影响上下文预算
- 提供"可发现性"——agent 知道有什么可以用，不会因为看不到而遗忘
- 索引条目用简短自然语言描述，让模型能正确判断何时需要加载

### L2 事实层（按需加载）

**作用**：环境事实、用户偏好、当前状态等结构化信息。

**类比**：参考手册中的具体条目

**示例内容**：
```json
{
  "user_preferences": {
    "language": "中文",
    "code_style": "Google style",
    "preferred_framework": "FastAPI",
    "timezone": "Asia/Shanghai"
  },
  "server_info": {
    "prod": "aws us-east-1, t3.large",
    "staging": "aws ap-southeast-1, t3.medium"
  }
}
```

**加载时机**：agent 判断当前任务需要这些信息时，主动 `file_read` 加载。

### L3 SOP 层（按需加载）

**作用**：标准操作流程、技能脚本——"做某件事的步骤"。

**类比**：操作手册中的具体章节

**示例内容**：
```markdown
## 部署 SOP
1. 运行测试: `pytest --cov`
2. 检查覆盖率 ≥ 80%
3. 构建镜像: `docker build -t app:latest .`
4. 推送: `docker push registry/app:latest`
5. 滚动更新: `kubectl rollout restart deployment/app`
6. 验证: `curl -f https://app.example.com/health`
```

**加载时机**：agent 识别到需要执行特定流程时加载对应 SOP。

### L4 原始日志（极少访问）

**作用**：完整对话历史，不做压缩，用于追溯和审计。

**类比**：档案室的原始卷宗

**特点**：
- append-only，无限增长
- 正常执行中不加载到上下文
- 仅在需要追溯历史决策、审计、或恢复时访问
- 对应 A4 中 Session 的"档案室"概念

## 四、与记忆工具的配合

GA 的两个记忆工具与四层架构的关系：

| 工具 | 作用于哪层 | 行为 |
|------|-----------|------|
| `update_working_checkpoint` | L1 + L2 | 更新当前工作进度，刷新索引和事实 |
| `start_long_term_update` | L2 + L3 | 将本次对话中的新发现沉淀为持久知识 |

**写入流程**：
```
Agent 发现新事实/模式
       │
       ├── 短期：update_working_checkpoint
       │         → 更新 L1 索引 + L2 当前状态
       │
       └── 长期：start_long_term_update
                 → 新增/修改 L2 事实条目
                 → 新增/修改 L3 SOP 步骤
                 → L4 自动追加原始日志
```

## 五、与其他方案的对比

| 方案 | L1 索引 | L2 事实 | L3 SOP | L4 日志 | 按需加载 |
|------|:-------:|:-------:|:------:|:-------:|:--------:|
| GA 四层架构 | ✅ | ✅ | ✅ | ✅ | ✅ |
| DeerFlow Memory | ❌（全量注入） | ✅ facts | ❌ | ❌ | ❌ |
| Claude Agent SDK | ❌ | ❌ | ❌ | ❌ | ❌（无内置记忆）|
| A2 当前设计 | ⚠️ 隐式 | ✅ L1 insights | ✅ Skill | ❌ | ⚠️ 部分 |

## 六、A2 适配分析

### 当前 A2 记忆体系映射

| GA 层级 | A2 对应 | 差距 |
|---------|---------|------|
| L1 索引层 | Skill 三级披露的 L1 元数据 + Memory insights 注入 | 未统一为一个"目录"，分散在多处 |
| L2 事实层 | `MemoryService` 的 GlobalFacts | ✅ 基本覆盖 |
| L3 SOP 层 | `SkillService` 的 Skill 全文注入 | ✅ 基本覆盖（按需加载） |
| L4 原始日志 | 当前缺失（进程内 message list，进程退出即丢失） | ❌ 需 Session 外部化（参见 A4） |

### 待增强方向

1. **统一 L1 索引层**：
   - 将 Skill 元数据、Memory facts 摘要、当前任务 checkpoint 统一为一个轻量索引块
   - 始终注入 system prompt 末尾，~200 token 预算
   - 格式示例：
     ```
     [可用知识] skills: deploy_sop, debug_playbook, code_review
     [用户偏好] 中文, Google style, FastAPI
     [当前进度] task 2/5 完成, 正在实现 auth 模块
     ```

2. **记忆工具化**（对应 A3 待补齐项）：
   - `save_checkpoint` tool：agent 主动保存工作进度 → 更新 L1 + L2
   - `learn_fact` tool：agent 主动沉淀新发现 → 更新 L2 facts
   - `update_sop` tool：agent 发现更好的操作流程 → 更新 L3

3. **L4 原始日志持久化**：
   - 对接 Session 外部化设计（A4）
   - 所有 message/tool_call/result 以 append-only 事件流写入持久层
   - 正常执行不加载，仅 `wake()` 恢复或审计时使用

4. **按需加载机制强化**：
   - 当前 Skill 已有关键词触发加载（L2 → L3 升级）
   - 增加 agent 主动 `file_read` 加载 facts/SOP 的能力
   - L1 索引提供足够信息让 agent 判断"何时需要加载什么"
