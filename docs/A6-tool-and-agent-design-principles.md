## 一、AskUserQuestion 工具三次迭代（真实案例）

**背景**：Claude 执行任务前需要向用户提问。开放式问题效率太低 → 目标：**提升人机"通信带宽"**。

### 第一次：ExitPlanTool 加参数 ✗

| 维度 | 说明 |
|------|------|
| 方案 | 在已有工具里塞进 questions 参数，改动最小，实现最快 |
| 失败原因 | ExitPlanTool 含义是"我的计划已定"，加了 questions 就变成"我有决定但还有疑问"，逻辑矛盾，Claude 无法调和，输出质量明显下降 |

**工程原则**：一个工具只能承载一种意图。

### 第二次：格式 Hack ✗

| 维度 | 说明 |
|------|------|
| 方案 | 工具不动，改 prompt 规定 Markdown 格式，后端解析渲染 UI |
| 失败原因 | 大模型输出是概率分布，格式约束是倾向不是保证。偏离任意一次，解析器崩溃，用户体验不可控。这不是 Claude 的 bug，是语言模型的基本特性 |

**工程原则**：核心信令路径不能靠格式约定。

### 第三次：AskUserQuestion 工具 ✓

| 维度 | 说明 |
|------|------|
| 方案 | 给"提问"行为建独立具名工具：弹出模态窗 → 阻塞循环 → 用户回答后恢复 |
| 成功原因 | JSON Schema 强制结构化输出；工具名与语义完全对应；阻塞机制控制节奏。Claude 自然、频繁、准确地调用它 — 语义与模型决策逻辑高度吻合 |

**工程原则**：工具语义贴合，模型自然愿意用。

### 设计原则总结

| 原则 | 解释 |
|------|------|
| **一个工具只能承载一种意图** | 混合意图让模型困惑，输出质量下降 |
| **核心信令路径不能靠格式约定** | 模型输出是概率分布，格式偏离不可避免 |
| **工具语义贴合，模型自然愿意用** | 工具名+参数结构与模型决策逻辑高度吻合时，调用率和准确率最高 |

## 二、为 Agent 提供上下文（Context Injection）

**Harness 职责**：提前整理运行边界、环境和约束，主动递给大模型。

**核心收益**：外围信息越精准，大模型的算力越能集中。

### 1. 注入地图（LocalContextMiddleware）

系统在启动时替 Agent 完成扫描。由中间件直接将当前**目录结构、工具路径结构化**地塞给大模型。

> "Agent 接手的就是一份详细作战地图，直接解题。"

### 2. 评估显性化（Testing Requirements）

模型不懂什么叫"可测试性代码"。系统明确告知：**你的代码会被程序化测试打分**，须顾及边缘用例。

> "避免代码在表面跑通，背地里 Bug 成堆。"

### 3. 时间预算（Time Budgeting）

模型天然不擅长预估时间，容易死磕。Harness 会在接近 Deadline 时**注入强警告**，引导模型停止发散，立刻收工作。

> "打断强迫症式的发散，防超时失败。"

## 三、日常工作流与核心总结

### 深度优先工作法

```
大目标 → 构建模块 → 逐个完成 → 解锁复杂任务
```

失败时不是"再试一次"，而是回到元问题：**"缺了什么能力？"**

### Ralph Wiggum Loop

```
编码 → 审查 → 测试 → 修复 → ↺
```

Agent 互审代码，人类甚至不需要审查 PR。

### Core Takeaway

> 当代码可以被**无限生成**，工程师的价值就从"**写代码**"迁移到了"**设计让代码产生的环境**"。

## 四、A2 适配分析

### 工具设计原则映射

| 原则 | A2 当前实践 |
|------|------------|
| 一个工具一种意图 | `commands.py` 中每个 Command 职责单一（PlanCommand / SpawnAgentCommand / ...） |
| 不靠格式约定 | Tool 定义使用 JSON Schema，强制结构化 |
| 语义贴合 | Tool 命名需进一步审查，确保与模型决策逻辑吻合 |

### Context Injection 映射

| 注入策略 | A2 对应 |
|----------|---------|
| 注入地图 | `ContextService` 的 `build_messages()` 注入项目结构 |
| 评估显性化 | Sprint Contract 验收标准（参见 A5） |
| 时间预算 | 当前缺失 — 需在 `ReActStepCommand` 中增加 deadline 警告机制 |

### 待增强方向

1. **工具命名审查**：逐一检查现有 tool 定义，确保名称、参数结构与模型决策语义一致。避免一个 tool 承载多种意图。

2. **时间预算机制**：
   - `AgentCommand` 接受 `timeout` 参数
   - 接近 deadline（如 80%）时注入 system reminder："时间即将耗尽，请立即收尾当前工作"
   - 超时后强制中断并返回部分结果

3. **LocalContext 自动注入**：
   - Agent 启动时自动扫描工作目录结构
   - 将目录树 + 关键文件摘要作为首轮上下文注入
   - 减少 agent "自行发现上下文"的探索成本

4. **深度优先 + Loop 工作流**：
   - PlannerService 生成的 TaskList 按依赖关系排序，支持深度优先执行
   - 引入 review → test → fix 循环直到验收通过
